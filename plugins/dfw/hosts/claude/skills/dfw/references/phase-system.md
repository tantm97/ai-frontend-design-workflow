# Phase: system (gate DS)

Goal: a complete, reviewed design system **before any screen**: tokens (color, type, spacing, shape, elevation, motion) and component masters with every variant and state, shown on the Studio's Design System page. Screens later only compose these components.

Skills (budget): base `frontend-design:frontend-design`; support `ui-ux-pro-max:ui-ux-pro-max` (palette/type data, UX rules) and `impeccable:impeccable` (`critique` on the system page). Marketing surface: Hallmark leads instead (custom mode with DESIGN.md).

Method: `references/design-system-thinking.md` (read it before changing any colour or size). Every decision gets a line in DESIGN.md `## Rationale`.

## Steps (inventory first, then design every master for this product)

The design system is designed, not copied. `dfw system init` writes only tokens, fonts and the style's motif master, plus an empty `design/system/inventory.json`; it copies no components. The starter kit's masters are a read-only reference for states and accessibility (`dfw system ref`, `dfw system ref <name>`), never a starting file: a copied master, or kit example content, is a MUST finding (`kit-copy`).

1. **Tokens + inventory.** `dfw system init --style <id>`, unless it was already run at G1 (it refuses to replace existing tokens; `--force` overwrites them). Then fill `design/system/inventory.json` from PRODUCT.md workflows and the screen blueprints: one entry per component the product needs, `{"name", "purpose" (its job in THIS product), "usedBy" (pages/screens), "states", "ref" (optional kit reference)}`. Start from the product's objects and moments (a merch shop: product-card, option-picker, cart-drawer; a tool crib: scan-slip, item-line, feedback-band), then add the generic pieces the screens actually need (app-shell, text, button...). Leave out anything no screen uses: no dialog without a dialog moment, no data-table without a table. `dfw system inventory` shows unbuilt entries, orphan masters and kit copies.
2. **Make the tokens the product's own** (this is what makes it look designed by a person):
   - Palette entries live in `color.palette.*` with names from the product's world (e.g. `lam`, `giay`, `kim`, `thep`, `vang-bang-keo`) and a `$description` that states the **usage rule** ("only for large surfaces with text ≥ 24px", "ornament only, never text"). Roles (`color.accent`, `color.ink`, ...) are aliases to palette entries.
   - Neutrals are tinted toward the concept (paper, steel, linen), shadows are tinted with a brand colour, never pure black/grey defaults.
   - Typography has real contrast: display sizes (`font.size.display-*`) at least ~2.5× body for marketing and ~1.8× for product UI; an eyebrow style; the display family used for titles and big numbers.
   - Keep the token names of the token contract (`references/design-format.md`); add new tokens as needed.
   - Fonts: pick from `references/type-pairings.md`. When any UI text is Vietnamese (lang vi or bilingual), every family rendering it must ship the `vietnamese` subset (`dfw fonts check "<Family>"`); English-only products may use Latin-only families (`dfw style apply <id> --fonts latin`; like `dfw system choose`, it stops on an edited `tokens.json` or `head.html` until the user agrees to `--force`). Update `design/system/head.html`.
   - Contrast: text 4.5:1, large text and UI boundaries 3:1. Write the ratios into DESIGN.md "Color".
   - Targets: size every tappable control on touch screens (phones, tablets, kiosks, counters) with `size.target-touch` (44px). `size.target-wcag` (24px) is the WCAG floor, never a design size. The layout check flags `touch-target` below 44px at breakpoints narrower than 1024px.
   - Asset paths inside masters (logos, placeholder images) use `{{base}}assets/...` so they resolve on screens, in the Studio and on the Design System page.
3. **Signature motifs** (1-2, from the style or the concept): masters in `design/system/components/motif.html` with a usage rule each ("once per view", "never behind text"). Brand assets (logos, ornaments, photos) go in `design/assets/` and are used as supplied, never redrawn.
4. **One app shell.** Design the `app-shell` master (navigation groups, brand, modes such as a counter/kiosk mode) for the product. Every screen is wrapped in `<dfw-use c="app-shell" current="<key>">`; a special mode (counter, kiosk) is a variant or a state of the same shell, never a different frame. Two screens with different chrome read as two products.
5. **Design every master in the inventory.** Write each master in `design/system/components/<name>.html` for this product and direction: its markup follows the job (a product card is a link with image, name, price and stock in words), its look follows the direction (borders, shadows, radius, type), every state in CSS (hover, focus-visible, active, disabled, loading, invalid/selected/sold-out where relevant), and `<dfw-examples>` show every variant, size and state with this product's real content. Before writing a generic piece, read `dfw system ref <name>` for the states and a11y details it must cover; do not paste it. Icons: `dfw icons search <words>` then `dfw icons add <names>`; never hand-draw icons. Masters that are independent can be written in parallel.
6. **Senior review + self-critique, 2 rounds:** `dfw system audit` (contrast, accent vs status hues, neutral temperature, hue budget, type rhythm and hierarchy, usage rules, rationale) — fix every MUST, fix or justify every SHOULD; then `dfw shoot --system`, score against `references/quality-rubric.md`, fix, repeat once. When you change colours, regenerate ramps with `dfw palette build` instead of nudging hex values by eye; when you change sizes, use `dfw type scale --write`.
7. **Present.** Run `dfw studio start`; it prints the Studio address and a `design system:` line. Write both links in your reply as bare URLs the user can click: the Studio on the Design System page (`<studio>?page=system`, for comments) and the page alone (`<studio>__dfw/system.html`). The page shows the concept, do/don't, palette with usage rules and contrast, type scale, spacing, motifs, assets, and a spec line per component. In chat: the inventory (each component and the screens that need it) and 2-3 decisions you want the user to look at. Then start `dfw comments wait --timeout 3600` in the background (Bash `run_in_background`) and follow `references/phase-review.md` > "Live comments": the user comments in the Studio and presses **Send to AI**, which wakes you.
8. On approval: update DESIGN.md (Components section lists every master with its use; the DS gate refuses masters missing from the inventory, inventory entries without a master, and kit copies; `## Rationale` ≥ 5 product-specific lines — the DS gate refuses without it), `dfw approve DS --note "<what was approved>"`, `dfw phase concepts`.

Changing the system after DS: allowed during concepts (it propagates to all screens); tell the user what changed. After G2 the system is frozen with the design.
