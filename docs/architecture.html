dfw: design-first frontend workflow

A Claude Code plugin that makes Claude design before it codes: discovery, a visual direction, a design system, then screens reviewed on a local Figma-like Studio. Only after you approve the design and the tech stack does it write real application code, and then it verifies the result against the design.

Claude Code pluginHTML/CSS + DTCG tokens5 approval gatesLocal StudioSingle-file binary

Architecture1. The big picture

dfw has three layers. core is the engine and knows nothing about Claude Code. adapter turns it into things Claude Code understands (a skill, agents, hooks). external skills are pinned copies of design skills that dfw calls when a phase needs them.

Design first

Designs are framework-neutral HTML/CSS plus W3C DTCG tokens, so they render anywhere and can be implemented in any stack.

Design system first

Tokens and component masters come before screens. Screens are built from component instances (<dfw-use>), not one-off markup.

You hold the gates

Five approvals (G1, DS, G2, G3, G4) are recorded only after you approve in chat or in the Studio. A hook blocks code writes before G2 and G3.

State lives in the project

Everything is plain files in .dfw/ and design/, so it can be committed and reviewed like code.

Architecture4. Who does what in a session

The main Claude conversation, guided by SKILL.md, is the only one that talks to you and records gates. It hands narrow jobs to agents and runs everything through the CLI.

What the skill does on every invocation

  1. LanguageOnce per session it asks which language to talk in (dfw lang). Files, code and commit messages always stay English.
  2. Statedfw status: no workflow yet → pick a mode; otherwise continue the current phase.
  3. ModeMaps your request to a mode (section 13) and runs dfw init.
  4. Read the phase referenceOnly the file for the current phase is loaded, which keeps context small.
  5. PoliciesBefore calling any external design skill it reads precedence.md and conflicts.md: your instruction > approved decisions > dfw rules > external skills.

Architecture5. Hooks: the automatic guardrails

Claude Code runs these itself, so they work even if Claude forgets a rule. Each one runs bin/dfw hook <name> (about 80 ms). If a hook hits an internal error it lets the action through rather than blocking your work. dfw pause turns them off for a project.

Network. The only Impeccable command dfw runs (impeccable detect) makes no network call, and dfw sets DO_NOT_TRACK=1, IMPECCABLE_NO_UPDATE_CHECK=1 and IMPECCABLE_HOOK_DISABLED=1 (in core/lib/config.mjs, and in the dfw overlay at the top of both launchers, scripts/impeccable and the Windows scripts/impeccable.cmd, each only when the user has not set the variable), so the defaults also apply when the model runs Impeccable directly. Two calls remain: the one-time engine download from GitHub (sha256-checked against a checksum file in the repo; dfw triggers it only from dfw check --setup / install), and, only when Impeccable's own new-design flow runs, an anonymous GET impeccable.style/api/roll with a random key and no project data. Full audit: docs/impeccable-network.md.

Architecture7. The dfw CLI (core/lib)

Every real action goes through dfw. cli.mjs parses the command and calls one of these modules.

workflow

state · gate · freeze · config · lang

Phase machine in .dfw/state.json, gate records, decisions log, design snapshots and their hashes, layered config (global → project → local), session language.

design system

tokens · color · fonts · style · icons

DTCG tokens.json → tokens.css; OKLCH palettes with contrast-picked roles; modular type scale; Google Fonts subsets; curated style guides; Lucide icons.

design system

system · system-page · dsaudit

Starter components from kits/base, component list/variants/props, the generated Design System page, senior audit (contrast, accent vs status hues, type rhythm, rationale).

screens

compose

Expands <dfw-use> component instances into full HTML with tokens, so screens stay in sync with their masters. Tags inside HTML comments are ignored; an instance without its closing tag is a component-unclosed error.

quality

lint · layout · check

lint: fast static rules. layout: renders screens at each breakpoint/state (also with grown lists) and finds overlap, clipping, overflow, missing anchors, voids. check: adds Impeccable, sloplint, copy-lint. lint and check take targets as design/…, ./design/…, absolute paths or paths relative to the current directory.

rendering

cdp · runtime

Drives your installed Chrome/Edge headless over the DevTools protocol; font cache; used by shoot and layout. Navigation and every protocol command have a timeout; the browser and its temporary profile are removed when the start fails and when dfw exits or is signalled. See section 8.

review

comments · inbox · edit · locate

Comment records and statuses (every read-modify-write runs under the lock directory .dfw/reviews/.lock, so the Studio and the CLI do not lose each other's writes), delivery to Claude via hooks, Studio direct edits written back to source (text, props, spacing, plus constrained move and layout ops; refused once G2 locks the design or in review-only), mapping a clicked element to its file and line. The undo journal keeps the newest 200 edits.

review

live · inspector

dfw review: a loopback-only proxy in front of your local dev server that adds click-to-comment to the running app (a strict CSP is extended with a per-response nonce for its own scripts only; a localhost app is served on localhost so its cookies apply; a request with a non-loopback Host, or a write from another origin, gets 403). dfw inspector setup: the pinned dev-only code-inspector-plugin that gives those comments a file:line:col; --write keeps the original config as <config>.dfw-backup.

code

stack

Detects the existing stack (package.json, frameworks, styling), stores the proposal for G3.

bridge

penpot-tokens · penpot

Optional Penpot bridge: tokens to and from Penpot's token file; screens rendered into a layer tree for the Studio-served Penpot plugin, and Penpot edits turned into comments (on screens, and on component master files for edits on the dfw components page). Input from Penpot is checked: reserved token names (__proto__, constructor, prototype) are refused, and an exportId that is not in the form dfw generates (px_…) is ignored, so it cannot name a file outside .dfw/penpot/exports/.

install

install · binary · hooks

Registers marketplace + plugins with Claude Code, downloads the binary and checks the browser; hook handlers.

Architecture8. Rendering & the single-file binary

How dfw starts

How screens are rendered

  1. Find a browserDFW_BROWSER / CHROME_PATH → a headless Chrome downloaded by dfw setup --browser (only over https from storage.googleapis.com) → installed Chrome, Edge, Chromium or Brave.
  2. Launch headlessOne browser per command with a temporary profile and --remote-debugging-port=0; dfw talks to it over Node's built-in WebSocket. Navigation and each command time out instead of hanging; the browser and the profile are removed on a failed start, on exit and on SIGTERM/SIGINT/SIGHUP.
  3. Render in parallelOne context per device scale, up to 6 pages at once; viewport set per breakpoint; wait for load and fonts.
  4. Font cacheGoogle Fonts requests are intercepted and served from ~/.config/dfw/cache/fonts, so repeat renders never hit the network.
  5. Measure or capturelayout evaluates geometry in the page; shoot captures PNGs (full page or one element).

Release pipeline

Push tag v<version> → a verify job first checks that the tagged commit is on main, runs npm test and build --check; then GitHub Actions builds darwin-arm64, darwin-x64, linux-x64, linux-arm64 and win32-x64 binaries with the official Node 26 LTS, smoke-tests each (including a real render), and publishes a release with SHA256SUMS. install.sh and dfw setup --binary verify that checksum before installing.

Architecture9. Studio & the comment loop

dfw studio start runs a small local server (studio/server.mjs) on 127.0.0.1:4600. The app is plain HTML/CSS/JS: a pannable canvas of iframes, one per screen × breakpoint × state, grouped by page. The server answers only requests whose Host is 127.0.0.1:<port> or localhost:<port>, and refuses writes (methods other than GET, HEAD, OPTIONS) whose Origin is another site, with 403: otherwise a web page you visit could post comments the agent reads as yours or edit design files, and a DNS-rebinding page could read the Studio.

Canvas

Every screen at every breakpoint and state side by side, plus the Design System page. Frames show the full page height by default (Full height toggle crops to the viewport). Pan, zoom, select layers, inspect styles and tokens.

Comments & pins

Pins mark commented elements. Click a pin to read the comment and thread. Toggle pins open → all → off with ShiftC.

Direct edit

Small text/style tweaks in the inspector are written back to the source file (undo with ⌘Z; the newest 200 edits are kept, and an edit whose file was deleted is skipped). Refused once the design is approved (G2) or in review-only mode.

Drag & resize

Drag a selected data-dfw-id element among its flex/grid siblings, or into an empty flex/grid container that has a data-dfw-id (op move, position inside): its source moves. Handles resize with snapping: grid column span, size.* token or 25–100% width, space.*/size.* min-height, written to a <style data-dfw-layout> block as [data-dfw-id='x']:not(#dfw) rules (the :not(#dfw) adds one id of specificity, so the edit beats class-based screen rules without !important); in a narrower breakpoint frame inside @media (max-width: <frame>px) (covered by e2e at two widths). If a stronger rule (id selector, inline style, !important) still wins, a toast names it. Reset to auto (op layout with value auto/null) removes the declaration or the whole rule. Ids that exist only in a component master are refused with a pointer to the master; slot content written in the screen can be moved. No free positioning.

Running app

dfw review start --url http://localhost:5173 (phase verify) proxies the app on loopback with a Comment button (or Alt/OptionC); HMR passes through. Comments land in the same inbox (provider: "dfw-live", the route, a screenshot in .dfw/shots/live/) with target.source from data-insp-path when the inspector is installed.

Penpot

The Studio serves the "dfw bridge" Penpot plugin at /__dfw/penpot/*. It builds boards from dfw penpot export; designer edits and Penpot comments come back as dfw comments (provider: "penpot"), never as HTML. Edits to main components on the dfw components page come back as comments on the master file (target.component, target.layer, target.source = the master's CSS rule or template line, matching tokens); typography, shadows, layer order and new variants are not sent back. No Penpot token or cloud call. Tested on fixtures only, not inside a running Penpot.

Present

P shows one frame full-window like a prototype; ← → step through the page. Pins are hidden by default.

Approve

Gates can be approved from Studio as well as chat; it records the same dfw approve.

Guide11. Install

Option A: no Node.js on the machine

curl -fsSL https://raw.githubusercontent.com/tantm97/ai-frontend-design-workflow/main/install.sh | sh

Downloads the binary for your OS, verifies its SHA-256, installs it to ~/.config/dfw/bin/<ver>/, links ~/.local/bin/dfw, then runs dfw install. Pin a version with DFW_VERSION=0.5.1.

Works only after a release has been published (tag v0.5.1 pushed and the release workflow finished).

Option B: with Node.js 22+

npx github:tantm97/ai-frontend-design-workflow

Same steps, from source. Flags: --host auto|claude|copilot|all, --scope user|project|local, --source <path|owner/repo>, --no-binary (stay on Node), --no-runtime (skip browser check).

What install does

  1. MarketplaceAdds or updates dfw-marketplace in Claude Code. If it is registered from a different source than --source, it is removed and added again.
  2. PluginsInstalls dfw and the seven design skills.
  3. BinaryDownloads the matching binary (failure is only a warning; Node keeps working).
  4. BrowserLooks for Chrome/Edge/Chromium/Brave; if none, downloads Google's headless Chrome once (same as dfw setup --browser; a failure is only a warning).
  5. DoctorPrints dfw doctor: everything should be green.

Restart Claude Code afterwards. Remove with dfw uninstall (project files stay).

Guide12. First project, step by step

  1. Open Claude Code in your project folder and describe what you wante.g. "Design an asset tracking web app for warehouse staff", or type /dfw new …. The dfw skill triggers on any frontend UI task.
  2. Pick a languageClaude asks once per session which language to talk in.
  3. Answer discovery questionsUsers, key tasks, data, devices, brand constraints. Upload requirement documents to design/assets/ if you have them. Claude writes PRODUCT.md.
  4. Choose a direction (G1)Read the 2–3 briefs (and sketches if offered). Reply with your pick or a mix: "Go with B, but warmer colours".
  5. Review the Design System (DS)Claude starts Studio and shows the DS page: palette, type scale, components and their states. Comment on anything, then say "approve DS".
  6. Agree blueprintsFor each screen: goal, layout, what's above the fold, data range. Confirm or adjust.
  7. Review screens in StudioScreens appear page by page. Use C to comment, check breakpoints and states, use Present to click through. Claude fixes and marks comments "fixed"; you resolve or reopen.
  8. Approve the design (G2)When every page is right: "approve G2". The design is frozen as v1 and a handoff is generated.
  9. Approve the stack (G3)Claude detects or proposes the framework and dependencies, for JavaScript projects including the dev-only code-inspector-plugin (for file:line in live comments). Approve or change.
  10. Implementation and verification (G4)Claude builds the app, then compares it with the design at each breakpoint and lists deviations. You can comment directly on the running app (dfw review). Accept to finish.
Check where you are at any time with "dfw status" in chat or dfw status in a terminal.

Reviewing the running app

In phase verify Claude runs dfw review start --url <dev server> and gives you a link: http://localhost:4700/… for a localhost app (the proxy listens on 127.0.0.1 and ::1, never 0.0.0.0, so the app's host-scoped login cookies still apply), otherwise http://127.0.0.1:4700/…. Press Comment (or Alt/OptionC, so the app's own C shortcut keeps working; never while typing in a field), click an element, write, ⌘/Ctrl Enter. Change the key with --shortcut <combo> or dfw config set review.shortcut <combo>; off leaves only the button. Claude opens target.source and fixes the code; HMR updates the page. Only local targets are accepted. The proxy answers only requests whose Host is localhost, 127.0.0.1 or [::1], and refuses comment posts from another origin (403). A strict Content-Security-Policy (header, Report-Only or <meta>) gets only the proxy origin and a per-response nonce for the injected scripts, and connect-src for the comment POST; nothing else is loosened. Pages that enforce Trusted Types are not supported yet.

Writing comments that get fixed right

  • One change per comment, pinned on the element it's about.
  • Say the outcome, not only the problem: "Status column should be a coloured badge, not plain text".
  • For system-wide changes (font, colour, spacing) say so: "Use this font across the whole product". Claude changes the tokens, not one screen.
  • When Claude marks a comment fixed, check it and resolve, or reopen with a reply.

Guide16. Troubleshooting

SymptomFix
Anything oddRun dfw doctor first; it checks runtime, Node version, browser, plugins and project state.

macOS warns about the binaryIt's ad-hoc signed, not notarized. Installing via curl | sh avoids the warning; a browser download triggers it.
sloplint / copy-lint "unavailable"Install Node 22+; dfw works without them.
Drag/resize refusedThe element needs a data-dfw-id and a flex/grid parent; not after G2, in review-only, on the Design System page or in Present. An id that exists only in a component master is refused: change the master, or comment.
"Saved, but … did not change"A stronger screen rule (id selector, inline style, !important) still sets that property; the toast names it. Remove it there (or ask Claude), then resize again.
Live comments have no file:lineThe app has no code-inspector-plugin (or runs a production build): dfw inspector setup.
dfw inspector setup --write: "cannot edit this project's bundler config automatically"The config has a shape dfw does not edit (for example a config function with a body): apply the printed change by hand. After a successful --write the original is in <config>.dfw-backup.

Known limitations

  • The write gate covers Edit/Write/MultiEdit/NotebookEdit; shell commands could still write files (forbidden by the skill, not enforced).
  • Impeccable is not fully offline: the one-time engine download and, in Impeccable's own new-design flow, an anonymous card-catalog request (see section 6).
  • Canvas drag and resize are constrained: reorder among flex/grid siblings and resize with snapping to grid spans and tokens; free-form absolute positioning is intentionally not supported (designs are responsive flow layouts that become real code). Dropping into a container works only for an empty flex/grid container with a data-dfw-id; other layout changes (new grid templates, nested containers, a component master's own layout) go through comments or the code. Colours and typography are changed in the design system (tokens or masters).
  • Penpot is an optional bridge, not a second source of truth: Penpot edits return as comments for the agent to apply, not as HTML. The plugin follows Penpot's documented plugin API but is tested on fixtures only (no running Penpot in CI).

Guide17. Developing dfw

node scripts/build.mjs              # core + adapter → plugins/dfw, notices
node scripts/build.mjs --check      # verify plugins/ is up to date
node --test tests/unit/*.test.mjs   # unit tests (npm test: 162 tests)
node tests/e2e/studio.e2e.mjs       # Studio end-to-end (needs Playwright, dev only; DFW_BROWSER picks the Chrome)
node scripts/build-binary.mjs       # local binary in dist/ (official Node build for portability)
git tag v0.5.1 && git push origin v0.5.1   # CI builds and publishes binaries
  • Edit core/ and adapters/, never plugins/dfw/ directly; rebuild after changes.
  • Bump the version in core/manifest.json and package.json together, then npm run build (the plugin and marketplace manifests are generated); the release tag must match.
  • Keep hooks fail-open and fast: they run on every edit and message.
  • Unit test files added with the audit fixes: audit-fixes (compose, lint targets, layout cache, undo, edit boundary), studio-guard (Host/Origin checks, comment lock), cdp (timeouts, cleanup, download host), inspector-shapes, install-paths (launcher fallback, Windows spawn, marketplace source, leftover check, upstream bot, shared core copy list), lighthouse, mcp-robust, penpot-hardening (each tests/unit/<name>.test.mjs).
  • validate also fails when a built plugin ships an upstream hook installer (install-hook(s).js|mjs|cjs) or an unresolved <skill-dir> placeholder; the Hallmark overlay deletes install-hook.mjs and lint-hook.mjs and resolves every <skill-dir>.
  • Release (release-binaries.yml): a verify job (tagged commit on main, npm test, build --check) must pass before any binary is built. The upstream bot opens one "blocked" issue per upstream commit and starts validate.yml on its pull requests (workflow_dispatch, actions: write). All workflow actions are pinned by commit SHA.
  • CI (.github/workflows/validate.yml): unit tests, build check and validate, plus an e2e job that installs a pinned Playwright library into RUNNER_TEMP and drives the runner's Google Chrome through DFW_BROWSER (screenshots uploaded on failure).
  • Live review is tested with fixtures and a headless browser (strict CSP, localhost cookies, the shortcut), not yet on real Vite/webpack/Next projects; inspector setup --write edits only Vite, webpack and Next configs.
